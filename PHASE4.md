# Phase 4 — RAG / AI Engine

## Architecture

```
User query
    │
    ▼
_extract_facts()  ── LLM call 1: restates user's own facts + domain, no legal claims
    │
    ▼
retrieve_legal_context()  ── rag_engine.py
    ├── hybrid_retrieve_laws()   ── BM25(bm25_laws.pkl) + Vector(chroma_laws) → RRF fusion
    └── hybrid_retrieve_cases()  ── BM25(bm25_cases.pkl) + Vector(chroma_cases) → RRF fusion
    │
    ▼
_generate_assessment()  ── LLM call 2: reasons ONLY over retrieved content,
    │                       cites by ref_id (L1, L2, ... / C1, C2, ...)
    ▼
_merge_citations()  ── code re-attaches REAL metadata for each cited ref_id;
    │                   drops any ref_id the LLM invented (doesn't exist in retrieval)
    ▼
Final structured dict + fixed disclaimer (appended in code, not left to the LLM)
```

`rag_engine.py` is imported by both modules. Module 1 (Document Risk Analyzer,
Phase 5/6) will call `retrieve_laws()`/`hybrid_retrieve_laws()` per clause;
Module 2 (`issue_analyzer.py`) calls `retrieve_legal_context()` once per
issue. Neither module touches `chroma_*`/`bm25_*.pkl` directly — `rag_engine.py`
is the only file that does, so index format changes never ripple outward.

## Retrieval methods, explained

**Dense (vector):** the query and every stored document were embedded with
`sentence-transformers/all-MiniLM-L6-v2` (384-dim). Chroma returns the
nearest documents by cosine distance. Good at matching *meaning* even when
wording differs (e.g. "landlord won't give my deposit back" ≈ "deficiency of
service" conceptually), weak at exact statutory numbers.

**Sparse (BM25):** classic keyword/term-frequency ranking over the same
documents. Good at exact terms ("Section 106", "IPC 420"), weak at
paraphrase — this was demonstrated concretely in Phase 3, where BM25 alone
missed the Consumer Protection Act section for a deposit-related query.

**Hybrid (RRF):** both methods return their own ranked list; each document's
final score is `Σ 1/(60 + rank)` across whichever list(s) it appears in.
RRF was chosen over trying to normalize BM25 and cosine scores onto a
comparable scale (which is fragile) — it only needs rank order from each
method, not directly comparable magnitudes.

**Deduplication:** law hits are deduped by `(act, section)` — the true
identity of a provision, since the same section can appear as multiple near
-identical embedded chunks. Case hits are deduped by `case_id`, because a
single judgment is chunked into many pieces during indexing (Phase 3) and a
query can otherwise return the same case 3 times under different ref_ids.

## Grounding / anti-hallucination design

This is the part your brief is strictest about (#8: "no fabricated laws,
cases, citations"), so it's enforced at more than one layer, not just by
prompting:

1. **Ref-id citation, not recall.** The LLM never has to remember or
   reproduce a section number or case name — it only has to point at
   something already retrieved and printed in front of it (`L1`, `C2`, ...).
2. **Code-side citation validation.** `_merge_citations()` looks up every
   `ref_id` the LLM used against what was actually retrieved. Anything not
   found is *dropped*, not passed through — logged as a warning instead. So
   even if the LLM invents a ref_id, it cannot reach the final output
   attached to real-looking (but fake) metadata.
3. **Fixed disclaimer.** Appended in Python, not generated by the LLM, so it
   can't be forgotten.
4. **Empty-retrieval handling.** If nothing relevant is retrieved, the
   context block literally says `(no relevant law sections retrieved)` /
   `(no relevant case law retrieved)`, and the prompt instructs the model to
   say so rather than fill the gap from its own training data.
5. **No verdict language.** The prompt explicitly forbids "you will win" /
   "the court will rule" framing and requires both supporting AND opposing
   considerations — a one-sided answer would itself be a signal something's
   wrong.

**What this does NOT guarantee:** the free-text fields (`issue_summary`,
`supporting_considerations`, `opposing_considerations`,
`possible_actions_or_remedies`) are still LLM-generated reasoning over the
retrieved context — they are not independently fact-checked. The grounding
guarantee applies specifically to `relevant_laws`/`relevant_cases`: anything
appearing there is traceable to `indian_legal_acts_master.json` or
`case_law_master.json`.

## Output schema

```json
{
  "issue_summary": "string",
  "legal_domain": "string",
  "key_facts": ["string", ...],
  "missing_facts": ["string", ...],
  "relevant_laws": [
    {"ref_id": "L1", "act": "...", "section": "...", "title": "...",
     "category": "...", "why_relevant": "...", "retrieval_score": 0.0}
  ],
  "relevant_cases": [
    {"ref_id": "C1", "case_id": "...", "case_name": "...", "domain": "...",
     "source": "...", "why_relevant": "...", "retrieval_score": 0.0}
  ],
  "supporting_considerations": ["string", ...],
  "opposing_considerations": ["string", ...],
  "possible_actions_or_remedies": ["string", ...],
  "lawyer_specialization": "string",
  "disclaimer": "fixed string, always present"
}
```

## Known limitations (carried over from Phase 3, still true here)

- **Case name quality:** 100 of 105 cases in the source dataset lack a clean
  "Party A v. Party B" title (see Phase 3 report) — `case_name` for those
  will show an appeal number/counsel line instead. This is real source data,
  not fabricated, but it's not pretty. Worth mentioning proactively in the
  viva.
- **Category field is coarse:** `category`/`domain` labels come from keyword
  heuristics, not a trained classifier — treat them as a hint, not ground
  truth, exactly as flagged in Phase 3 EDA.
- **BNS not included** (dead source, documented future scope).
- **Two LLM calls per query** (fact extraction + assessment) — acceptable
  latency for a demo on Groq's fast inference, but worth mentioning if asked
  about production cost/latency in the viva.
- **`why_relevant` text is LLM-generated**, not verified against the cited
  provision's content — it's reasoning *about* real, retrieved text, but the
  reasoning itself isn't separately fact-checked.
